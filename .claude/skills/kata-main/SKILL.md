# kata-main

設計の bad / good を **実際に動かして差分を見る** ためのエントリポイントを書く。

このリポジトリの目的は「読むだけだと腹落ちしない悪さを、エラーメッセージや
挙動の差分で見る」こと。よって main.php は動作確認スクリプトではなく、
**欠陥や不変条件を目に見えるようにする教材**として書く。

## 前提となるディレクトリ規約

```
chapter-NN/
├── bad/
│   ├── ClassName.php   # 定義のみ。実行コードを混ぜない
│   └── main.php        # エントリポイント。小文字
└── good/
    ├── ClassName.php
    └── main.php
```

- 定義ファイルはクラス名と同じ大文字始まり、エントリポイントは小文字 `main.php`
- 読み込みは必ず `require_once __DIR__ . '/ClassName.php';`
  - `__DIR__` は末尾スラッシュを含まない。連結側の先頭に `/` が要る
  - `'./ClassName.php'` と書くと `bad./ClassName.php` になって落ちる
- 大文字小文字だけを変えるリネームは **削除 → 作成** の順で行う
  - macOS は大小を区別しないため、`git mv` なしだと追跡名と実ファイルがズレ、
    `core.ignorecase=true` により `git status` に永久に出てこない
- bad と good で同名クラスを定義しない。同一プロセスで両方 require すると
  `Cannot declare class/enum ..., because the name is already in use` で落ちる
  - 例: bad 側は `MoneyData` / `MoneyManager` のように、悪さが名前に出る形にする

## 引数

対象は引数で受け取る。受け付ける形は4つ。

| 渡されるもの | 例 | 対象 |
|---|---|---|
| 定義ファイルのパス | `chapter-04/bad/AttackPower.php` | そのファイルがあるディレクトリ |
| ディレクトリ | `chapter-04/bad` | そのディレクトリ |
| 章 | `chapter-04` / `04` / `4` | その章配下の `bad` と `good` 両方 |
| なし | — | 下のフォールバックで探索 |

- 章だけを渡された場合、`bad` と `good` の両方が対象になる。
  ただし定義ファイルが1つも無いディレクトリは飛ばす
- `04` や `4` のような数字だけの指定は `chapter-04` に解決する（ゼロ埋め2桁）
- 存在しないパスを渡されたら、勝手に近いものを推測せず、
  実在する章の一覧を出して確認する

### フォールバック（引数なし）

定義ファイルはあるが `main.php` が無いディレクトリを探す。

```bash
find chapter-* -mindepth 1 -maxdepth 1 -type d | sort | while read -r d; do
  [ -n "$(find "$d" -maxdepth 1 -name '*.php' -not -name 'main.php' -print -quit)" ] || continue
  [ -f "$d/main.php" ] || echo "$d"
done
```

- `main.php` 以外の `.php` が1つも無いディレクトリは候補にしない
  （空の `good/` を作った直後に誤爆させないため）
- zsh では `chapter-*/*/` の glob が空ディレクトリで
  `no matches found` を出すので、上記の `find` 版を使う
- 結果の扱い:
  - **0件** — 「全て作成済み」と伝えて終わる。何も作らない
  - **1件** — そのまま対象にする
  - **複数** — 一覧を出して、どれを作るか確認する。黙って全部作らない

## 手順

1. 上の規則で対象ディレクトリを確定し、定義ファイルを読んで
   bad / good どちらかを判定する
2. クラスの性質を見て、下のカタログから**該当する観点だけ**を選ぶ
   - 網羅しない。1ファイルに詰め込むと焦点がぼやける。2〜4件が目安
3. 出力規約に従って main.php を書く
4. `php -l` と実行で確認する
5. 実行結果を報告する。**期待通りのエラーが出ているかまで見る**
   - bad は「落ちるのが正しい」ケースがある。エラー = 失敗ではない

## 確認観点カタログ — bad

対象クラスの性質に応じて選ぶ。

### 生成の不完全さ
- **未初期化のまま使う** — typed property は初期値なしだと
  `Error: Typed property X::$y must not be accessed before initialization`。
  `new` は成功するのに使う時まで壊れていることが分からない、が肝
- **不完全なまま正常っぽい答えが返る** — 一部のプロパティだけ埋めて操作すると、
  未設定の項目を無視した「もっともらしい値」が返る。
  **落ちるより怖い**ので、落ちるケースより優先して見せる価値がある

### 生成後の破壊
- **public プロパティでバリデーション迂回** — `$obj->value = -999;`
  コンストラクタが保証したはずの不変条件を生成後に壊せる
- **参照共有による波及** — PHP のオブジェクトは代入で参照が渡る。
  `$b = $a;` して `$a->mutate()` すると `$b` も変わる。
  可変クラスの事故として最も分かりやすい。`$a === $b` を先に出すと因果が読める

### 型の緩さ
- **暗黙の型変換** — `declare(strict_types=1)` が無いと `int` 宣言に
  `"100"` も `true` も無言で通る。`1.5` だけは Deprecated が出る。
  **警告が出ない string / bool の方が危険**という順序で見せる
- **不正な文字列が素通り** — 通貨や区分を `string` で持つと `"US"` のような
  タイポが生成時に通り、バグが後段まで遅延する
- **意味を成さない操作が通る** — 金額 × 金額のように単位が壊れる計算。
  シグネチャ自体が間違っていても型が許してしまう
- **戻り値で型情報が失われる** — `add(): int` のように生の型で返すと、
  以降その値は何の単位かを失う

### 責務の分離
- **データクラス + 操作クラス** — 状態を持つだけのクラスと、それを操作する
  マネージャに分けると、不変条件をどこも守らなくなる

## 確認観点カタログ — good

bad と**同じ操作を試みて、守られることを示す**のが基本。

- **生成時に必ず有効** — `var_dump` して全プロパティが埋まっていること
- **不正値は生成時に例外** — `try`/`catch` でメッセージを表示する
- **不正な値がそもそも書けない** — enum 化した通貨など。
  実行時検証ではなく「コードに書けない」ことが成果なので、
  無理に実行時テストを書こうとしない
- **操作しても元が変わらない** — `return new self(...)` する不変クラスは、
  操作後に元インスタンスが無傷であることを前後比較で示す
- **外部入力の変換だけが検証点** — `Currency::from()` は `ValueError`、
  `tryFrom()` は `null`。文字列から型への変換の一点に検証が集約されたことを示す

## 出力規約

- **`printf` で桁を揃える**。`%3d` などで数値を縦に並べ、変化を目で追えるようにする
- **前後を必ず並べる**。「初期状態」の行がないと何が変わったか分からない
- **因果を先に置く**。`$a === $b` の判定のように、事故の原因になる事実を
  結果より先に出力する
- **ラベルは日本語**。全角の幅を揃えて左端を合わせる
- **矢印コメントで注目点を示す** — `<- B には何もしていない`
- `var_dump` は構造を見せたいとき（good の完全性の証明など）に使い、
  値の変化を追うときは `printf` を使い分ける

出力例:

```
同一インスタンスか : yes
初期状態           : A =  50 / B =  50
A を +50 強化      : A = 100 / B = 100  <- B には何もしていない
```

## 例外の受け方

後続の検証に到達させたいときは try/catch で受ける。捕まえる型を間違えると
そのまま Fatal error になるので注意する。

| 事象 | 投げられる型 |
|---|---|
| 未初期化プロパティへのアクセス | `Error` |
| 型宣言に合わない引数 | `TypeError` |
| enum の `from()` に不正な値 | `ValueError` |
| 自前のバリデーション | `InvalidArgumentException` |

`TypeError` / `ValueError` は `Exception` ではなく `Error` 系なので、
`catch (Exception $e)` では捕まらない。まとめて受けるなら `catch (Throwable $e)`。

**1ケースだけ見せて終わるなら catch しない**方がいい。Fatal error のスタックトレースが
「どこで壊れたか」を語ってくれるので、教材としてはそのまま出す価値がある。

## やらないこと

- 観点を全部盛りにしない。章の主張に関係ない欠陥まで並べると焦点が消える
- bad の警告や静的解析エラーを消しにいかない。**怒られること自体が bad の証明**。
  消したくなったら、コメントで「この警告が出るのが主旨」と明記する
- good で「書けないもの」を実行時にテストしようとしない
